# خطة تحويل حاسبة الشبابيك إلى منصة SaaS متعددة العملاء

## وثيقة تنفيذية وتقنية --- من التطبيق الحالي إلى منتج تجاري باشتراكات

**الهدف:** تحويل حاسبة الشبابيك الموجودة إلى خدمة ويب مدفوعة (SaaS)
يستطيع كل صاحب ورشة التسجيل فيها، وتجربتها 7 أيام بعد تسجيل وسيلة دفع
صالحة، ثم يبدأ الاشتراك المدفوع تلقائياً بعد انتهاء التجربة ما لم يُلغِ
العميل قبل موعد التجديد.

**مبدأ التنفيذ:** لا تعِد بناء الحاسبة ولا تغيّر معادلاتها أثناء تأسيس
المنصة. افصل منطق الحساب الحالي عن نظام الحسابات والاشتراكات، ثم اربطهما
تدريجياً واختبر النتائج مقابل النسخة الأصلية.

# 1. ملخص المنتج والقرارات الأساسية

## 1.1 ما الذي تبيعه؟

أنت لا تبيع «حاسبة مقاسات» فقط. أنت تبيع مساحة عمل رقمية لكل ورشة
ألمنيوم/شبابيك، تشمل:

-   حاسبة الشبابيك الحالية بأنواعها وقواعدها كما هي.
-   حفظ المشاريع والرجوع إليها لاحقاً.
-   حفظ تفاصيل كل مشروع: الفتحات، المقاسات، الكميات، النتائج،
    والملاحظات.
-   إدارة أنواع الشبابيك الأساسية.
-   إنشاء أنواع مخصصة ضمن حدود الباقة، أو طلب أنواع تحتاج إلى تطوير
    برمجي مدفوع.
-   إعداد أسعار المواد والإكسسوارات والتكاليف الخاصة بكل ورشة.
-   حسابات مستخدمين وصلاحيات.
-   اشتراك وتجربة مجانية وفوترة وإدارة حساب.
-   لوحة إدارة خاصة بك لمتابعة العملاء والاشتراكات والطلبات.

# 2. الرسم الهيكلي العام للمنصة

``` text
                         العملاء
                            |
                     دومين المنتج
                            |
                    واجهة تطبيق الويب
                            |
          +-----------------+------------------+
          |                 |                  |
       تسجيل الدخول      مساحة العمل       إدارة الحساب
          |                 |                  |
   Firebase Auth       حاسبة الشبابيك      الباقة/الدفع
          |                 |                  |
          +-----------------+------------------+
                            |
                    طبقة الخادم الآمن
                (API / Cloud Functions / Cloud Run)
                            |
       +--------------------+----------------------+
       |                    |                      |
  محرك الحسابات       صلاحيات المستأجر       الاشتراكات
  الحالي دون تغيير     والتحقق من الملكية      وحالة التجربة
       |                    |                      |
       +--------------------+----------------------+
                            |
                       قاعدة البيانات
                            |
       +--------------------+----------------------+
       |                    |                      |
    الشركات             المشاريع                الأنواع
    والمستخدمون         وتفاصيلها             والأسعار
       |
  سجل الاشتراك والدفع والطلبات
                            |
                    مزود الدفع الخارجي
                            |
                 Webhooks موثوقة إلى الخادم

                 لوحة إدارة مالك المنصة
            العملاء / الاشتراكات / الدفع / الدعم
```

## 2.1 مكونات المنصة ولماذا تحتاجها

1.  **واجهة الويب:** ما يراه المستخدم؛ التسجيل، لوحة العمل، الحاسبة،
    المشاريع، الفواتير والإعدادات.
2.  **Authentication:** إثبات هوية المستخدم وإدارة الجلسات واستعادة كلمة
    المرور.
3.  **قاعدة البيانات:** تخزين الشركات والمشاريع والأنواع والإعدادات
    وسجلات الدفع.
4.  **طبقة الخادم:** تنفيذ العمليات الحساسة، مثل إنشاء التجربة وتفعيل
    الاشتراك والتحقق من الدفع.
5.  **محرك الحاسبة:** منطق الحساب الحالي. يجب أن يبقى مستقلاً عن الاشتراك
    والواجهة قدر الإمكان.
6.  **مزود الدفع:** حفظ وسيلة الدفع وإجراء الخصم المتكرر وإرسال إشعارات
    حالة الدفع.
7.  **لوحة الإدارة:** إدارة المنصة من طرفك دون الحاجة إلى تعديل قاعدة
    البيانات يدوياً.
8.  **المراقبة والنسخ الاحتياطي:** اكتشاف الأعطال واسترجاع البيانات.

# 3. رحلة التسجيل والتجربة والدفع

هذه أهم نقطة تجارية في النظام. المطلوب أن يسجل المستخدم وسيلة دفع صالحة
قبل بدء التجربة، وألا يُخصم منه الاشتراك إلا بعد مرور 7 أيام.

## 3.1 رحلة العميل المقترحة

``` text
زيارة الموقع
    |
صفحة تعريفية + الأسعار
    |
إنشاء حساب
(الاسم، البريد، كلمة المرور، اسم الورشة)
    |
تأكيد البريد الإلكتروني
    |
اختيار الباقة
    |
إدخال وسيلة الدفع عبر صفحة مستضافة وآمنة من مزود الدفع
    |
حفظ وسيلة الدفع/إنشاء تفويض للاشتراك دون خصم فوري
    |
تأكيد المزود أن وسيلة الدفع صالحة ومهيأة للاشتراك
    |
إنشاء تجربة مجانية لمدة 7 أيام
    |
الوصول إلى التطبيق والميزات المسموحة
    |
هل ألغى العميل قبل نهاية التجربة؟
       /                 \
     نعم                 لا
      |                   |
إلغاء التجديد       انتهاء 7 أيام
وحفظ الحساب             |
                 محاولة تحصيل قيمة الاشتراك
                       |
                +------+------+
                |             |
              نجح            فشل
                |             |
          اشتراك فعال     حالة متأخر/فشل دفع
                              |
                     إعادة المحاولة وفق سياسة
                     المزود + إشعار العميل
```

## 3.2 ما معنى «تسجيل بطاقة دون خصم»؟

اطلب من مزود الدفع دعم واحد من الآتي:

-   **Setup / Save Payment Method:** حفظ وسيلة الدفع وتوثيقها دون تحصيل
    قيمة الاشتراك.
-   **Subscription with Trial:** إنشاء اشتراك يبدأ تحصيله بعد 7 أيام مع
    تسجيل وسيلة الدفع.
-   **Off-session recurring payment:** السماح للمزود بمحاولة التحصيل
    لاحقاً وفق موافقة العميل وشروط الشبكة.

لا تفترض أن كل مزود يدعم هذه الوظائف بالطريقة نفسها. اطلب من المزود
تأكيداً كتابياً أو اختبر ذلك في بيئة Sandbox.

**تنبيه مهم حول التفويض المسبق:** بعض البوابات قد تنفذ تحققاً بمبلغ صفري
أو تفويضاً مؤقتاً صغيراً. التفويض المؤقت قد يظهر كحجز على البطاقة ثم يُرفع،
وهو ليس بالضرورة خصماً نهائياً. لا تعد العميل بأن البطاقة لن يظهر عليها أي
تحقق إلا بعد التأكد من طريقة المزود والبنك.

## 3.3 متطلبات مزود الدفع

قبل اختيار المزود، تأكد من:

-   قبول شركة/تاجر مسجل في الأردن أو وضعك القانوني الفعلي.
-   دعم بطاقات العملاء من البلدان التي تستهدفها.
-   دعم الاشتراكات المتكررة (Recurring).
-   دعم حفظ وسيلة الدفع للاستخدام اللاحق بموافقة واضحة.
-   دعم تجربة مجانية تبدأ بعد تسجيل وسيلة الدفع.
-   دعم إلغاء التجديد من حساب العميل.
-   دعم Webhooks لتأكيد نجاح الدفع وفشله وإلغاء الاشتراك.
-   توفير بيئة اختبار Sandbox.
-   توفير صفحة دفع مستضافة أو عناصر دفع آمنة، بحيث لا تمر بيانات البطاقة
    عبر خادمك.
-   وضوح الرسوم، العملات، التسوية البنكية، الاسترداد والنزاعات.
-   دعم 3-D Secure / SCA عند الحاجة.

لا تخزن رقم البطاقة الكامل أو رمز CVV أو تاريخها في Firestore أو خادمك.
خزّن فقط معرف العميل ومعرف وسيلة الدفع ومعرف الاشتراك لدى مزود الدفع،
والحالة والبيانات غير الحساسة اللازمة للتشغيل.

## 3.4 بوابة الدفع في الأردن

لا تفترض أن Stripe متاح للتاجر الأردني لمجرد أنه معروف عالمياً. تحقق من
قائمة البلدان المدعومة وشروط فتح حساب التاجر وقت التنفيذ. قارن مزودين
إقليميين/محليين مثل بوابات الدفع الأردنية أو الإقليمية التي يمكنها دعم
الاشتراكات، واطلب منهم إجابة صريحة عن «تسجيل بطاقة الآن، بدء الخصم بعد 7
أيام، ثم خصم شهري تلقائي».

إذا لم يدعم مزود محلي الاشتراكات المتكررة أو حفظ البطاقة، فلن يحقق شرط
المنتج كما هو. لا تعتمد على تذكير العميل بالدفع يدوياً كبديل إلا إذا قررت
تغيير نموذج الاشتراك.

## 3.5 نص الإفصاح عند التسجيل

اعرض قبل تأكيد الاشتراك نصاً واضحاً، مع اسم الباقة والسعر والعملة ودورية
الخصم وتاريخ أول خصم المتوقع:

> تبدأ تجربتك المجانية لمدة 7 أيام بعد تأكيد وسيلة الدفع. لن يتم تحصيل
> رسوم الاشتراك خلال فترة التجربة. بعد انتهائها، سيتم تحصيل \[السعر\] كل
> \[شهر/سنة\] تلقائياً باستخدام وسيلة الدفع المسجلة، ما لم تلغِ قبل موعد
> التجديد. يمكنك الإلغاء من إعدادات الحساب. قد يجري مزود الدفع تحققاً أو
> تفويضاً مؤقتاً للبطاقة وفق إجراءات البنك.

يجب أن يوافق المستخدم صراحة على شروط الاشتراك والتجديد التلقائي وسياسة
الخصوصية. سجّل وقت الموافقة ونسخة النص التي وافق عليها.

## 3.6 قواعد دورة الاشتراك

الحالات المقترحة:

-   `pending_payment_method`: بدأ التسجيل ولم تكتمل وسيلة الدفع.
-   `trialing`: تجربة مجانية فعالة.
-   `active`: اشتراك مدفوع فعال.
-   `past_due`: تعذر تحصيل الدفعة.
-   `canceled`: أُلغي التجديد.
-   `expired`: انتهى الوصول وفق السياسة.
-   `incomplete`: لم يكتمل إعداد الاشتراك.

قواعد مهمة:

-   يبدأ عدّ الأيام السبعة فقط بعد تأكيد مزود الدفع حفظ وسيلة الدفع
    وإنشاء الاشتراك التجريبي.
-   خزّن `trial_started_at` و`trial_ends_at` بتوقيت UTC، واعرض الوقت
    محلياً.
-   لا تسمح بتجربة ثانية بمجرد إنشاء بريد آخر إذا كان ذلك مخالفاً لسياسة
    العرض؛ ضع ضوابط معقولة دون جمع بيانات زائدة.
-   الإلغاء أثناء التجربة يمنع أول خصم، مع تحديد هل يستمر الوصول حتى
    نهاية الأيام السبعة أم يتوقف فوراً.
-   فشل الدفع لا يحذف المشاريع.
-   نفّذ إعادة المحاولة والإشعارات وفق إمكانات مزود الدفع وسياسة معلنة.
-   اجعل استقبال Webhooks آمناً وقابلاً لإعادة الإرسال دون تكرار الخصم أو
    إنشاء أحداث مكررة (Idempotency).
-   لا تغيّر حالة الاشتراك بناءً على صفحة نجاح في المتصفح؛ مصدر الحقيقة هو
    إشعار المزود والتحقق من الخادم.

# 4. تقسيم قاعدة البيانات وعزل العملاء

## 4.1 نموذج الحسابات

استخدم مفهوم **Tenant / Workspace**. الـTenant هو الورشة أو الشركة التي
تملك بياناتها. قد يكون للورشة مستخدم واحد في البداية، ثم تضيف موظفين
لاحقاً.

``` text
users
  userId
  email
  displayName
  createdAt
  authProviderId

tenants
  tenantId
  businessName
  ownerUserId
  createdAt
  status
  locale
  currency

tenant_members
  tenantId
  userId
  role
  joinedAt
```

الأدوار المقترحة:

-   `owner`: مالك الورشة؛ إدارة الاشتراك والموظفين وكل بيانات الورشة.
-   `admin`: إدارة المشاريع والأنواع والأسعار، دون صلاحيات الفوترة
    الحساسة إلا إذا سمحت.
-   `operator`: استخدام الحاسبة وإنشاء/تعديل المشاريع.
-   `viewer`: قراءة المشاريع فقط.

## 4.2 نموذج بيانات المشاريع

``` text
tenants/{tenantId}/projects/{projectId}
  name
  customerName
  projectAddress
  notes
  status
  createdAt
  updatedAt
  createdBy
  calculationVersion
  pricingSnapshot

tenants/{tenantId}/projects/{projectId}/items/{itemId}
  windowTypeId
  typeNameSnapshot
  width
  height
  quantity
  inputsSnapshot
  calculatedResults
  unitCostSnapshot
  totalCostSnapshot
  createdAt
```

احفظ نسخة من المدخلات والنتائج والأسعار المستخدمة عند الحساب. هذا مهم
جداً: تعديل سعر مادة أو معادلة نوع لاحقاً يجب ألا يغيّر مشروعاً قديماً بأثر
رجعي.

## 4.3 الأنواع الأساسية والمخصصة

``` text
global_window_types/{typeId}
  name
  description
  calculationEngineKey
  version
  enabled

tenants/{tenantId}/custom_window_types/{typeId}
  name
  description
  configuration
  calculationEngineKey
  calculationVersion
  status
  createdAt
  createdBy
  pricingModel
```

قسّم الأنواع إلى ثلاثة أصناف:

1.  **أنواع عامة أساسية:** توفرها المنصة لكل العملاء، وتتحكم أنت بنسخها
    وتحديثاتها.
2.  **أنواع قابلة للتهيئة:** يستطيع العميل إنشاءها من خيارات مسموحة
    مسبقاً، مثل اختيار قطاعات أو إكسسوارات أو قواعد سعر، دون كتابة كود.
3.  **أنواع تتطلب تطويراً:** تحتاج معادلة أو سلوكاً جديداً؛ يرسل العميل
    طلباً، وتراجع أنت المتطلبات وتحدد السعر والمدة قبل التنفيذ.

لا تسمح للعميل بإدخال JavaScript أو كود تنفيذي داخل إعداد النوع. استخدم
إعدادات محددة ومتحققاً منها، أو محرك حسابات تملكه أنت.

## 4.4 الأسعار والإعدادات

``` text
tenants/{tenantId}/pricing_settings/{settingsId}
  currency
  materialPrices
  accessoryPrices
  laborCosts
  wastePercent
  updatedAt
  updatedBy
```

حدد هل السعر يُحفظ لكل ورشة فقط أم يمكن أن يكون لكل مشروع سعر خاص. ابدأ
بإعدادات افتراضية للورشة، مع إمكانية حفظ لقطة سعرية لكل مشروع.

# 5. قواعد عزل البيانات والأمان

هذه ليست خطوة تجميلية. خطأ واحد في العزل قد يكشف مشاريع ورشة لورشة أخرى.

## قواعد إلزامية

1.  كل سجل خاص بعميل مرتبط بـ`tenantId`.
2.  لا تعتمد على `tenantId` يرسله المتصفح وحده؛ تحقق أن المستخدم عضو في
    هذه الورشة.
3.  فعّل قواعد Firebase Security Rules لكل مجموعة/مسار.
4.  امنع القراءة والكتابة الافتراضية؛ ابدأ بالمنع ثم افتح الصلاحيات
    اللازمة.
5.  لا تضع مفاتيح Admin SDK أو أسرار مزود الدفع في كود المتصفح أو مستودع
    GitHub.
6.  لا تسمح للمتصفح بتعديل `subscription.status` أو `trialEndsAt` أو
    `planId`.
7.  لا تعتمد على إخفاء زر الميزة المدفوعة في الواجهة؛ تحقق من الباقة على
    الخادم أيضاً.
8.  استخدم App Check عند ملاءمته لتقليل الطلبات الآلية غير الموثوقة.
9.  سجّل عمليات الإدارة الحساسة: من غيّر الاشتراك؟ من عدّل نوعاً؟ متى؟
10. ضع سياسة نسخ احتياطي واختبر الاسترجاع فعلياً.
11. اختبر حسابين مستقلين، وحاول عمداً الوصول إلى بيانات الحساب الآخر.
12. راجع قواعد Firestore باستخدام Emulator Suite قبل النشر.

**تنبيه بنيوي:** Firestore لا يفرض علاقات SQL أو قيوداً مركبة بالطريقة
نفسها. يجب تصميم مسارات البيانات وقواعدها بعناية، وتجنب نسخ البيانات
الحساسة إلى أماكن يمكن الوصول إليها من العميل.

# 7. الباقات والميزات المدفوعة

ابدأ بباقتين أو ثلاث فقط. لا تكثر الخيارات في البداية.

## نموذج بيع الأنواع الإضافية

-   النوع القابل للتهيئة ذاتياً: ضمن الباقة أو بعدد محدد.
-   النوع الذي يتطلب برمجة: عرض سعر مستقل يدفعه العميل قبل بدء التطوير.
-   لا تَعِد بأن أي نوع يطلبه العميل سيضاف تلقائياً.
-   حدّد هل النوع المطور مخصص للعميل وحده أم يمكن تحويله لاحقاً إلى ميزة
    عامة، واحصل على موافقته على ذلك.
-   احتفظ بإصدارات الأنواع حتى لا تتغير نتائج المشاريع السابقة.

# 8. الحفاظ على الحاسبة الحالية ودقة المعادلات

هذه المرحلة ذات أولوية قصوى لأن قيمة المنتج قائمة على صحة الحسابات.

## قبل أي تعديل

1.  احفظ نسخة أصلية غير معدلة من المشروع.
2.  ارفعها إلى مستودع GitHub خاص.
3.  سجّل الأنواع الأربعة الحالية والمدخلات والمخرجات لكل نوع.
4.  أنشئ مجموعة حالات اختبار ثابتة (Golden Test Cases).
5.  سجّل حالات المقاسات الصغيرة والكبيرة والحواف والقيم الفارغة والمدخلات
    غير الصحيحة.
6.  احفظ لقطات من نتائج النسخة الحالية للمقارنة.

## طريقة الفصل

``` text
واجهة المستخدم
    |
    +---- تسجيل الدخول والصلاحيات
    |
    +---- إدارة المشاريع
    |
    +---- إدارة الأنواع والأسعار
    |
    +---- محرك الحساب الحالي
              |
         دوال الحساب الحالية
         دون إعادة كتابة أثناء المرحلة الأولى
```

## شروط قبول التعديل

-   نتائج المدخلات المرجعية مطابقة تماماً للنسخة الأصلية.
-   لا يتغير سلوك الأنواع الحالية دون طلب واضح.
-   يستطيع كل عميل حفظ مشروعه واستعادته.
-   تعديل الأسعار لا يغير لقطة المشروع القديمة.
-   النوع المخصص لا يؤثر على حسابات العملاء الآخرين.
-   يمكن الرجوع إلى إصدار سابق من التطبيق عند حدوث خلل.

# 9. التقنية والخدمات التي تحتاجها

## 9.1 أدوات التطوير

  -----------------------------------------------------------------------
  الأداة                              لماذا تحتاجها؟
  ----------------------------------- -----------------------------------
  Google AI Studio                    تطوير التطبيق بمساعدة الذكاء
                                      الاصطناعي وتجربة النشر

  Claude                              مراجعة المتطلبات والكود والتغييرات

  GitHub Private                      النسخ والإصدارات والتعاون والرجوع

  Firebase Console                    إدارة Authentication وFirestore
                                      والقواعد

  Google Cloud Console                إدارة Cloud Run والفوترة والسجلات

  Firebase Emulator Suite             اختبار قواعد البيانات والمصادقة
                                      محلياً
  -----------------------------------------------------------------------

استخدم AI Studio وClaude كمساعدين، لكن لا تسمح لأي منهما بإعادة بناء
التطبيق بالكامل دفعة واحدة. اطلب تغييراً صغيراً، راجعه، اختبره، ثم ادمجه.

## 9.2 اختيار قاعدة البيانات

**Firebase Authentication** مناسب لإدارة التسجيل والدخول.

أما قاعدة البيانات فهناك خياران:

### الخيار A: Cloud Firestore

مناسب عندما تكون البيانات عبارة عن مشاريع ومستندات وأنواع وإعدادات،
ويكون التطبيق مبنياً أصلاً على Firebase.

مزاياه: - تكامل جيد مع Firebase Authentication. - قواعد أمنية مباشرة. -
لا تحتاج لإدارة خادم قاعدة بيانات بنفسك. - مناسب للبدء السريع.

انتبه إلى: - تصميم الفهارس والاستعلامات. - تكاليف القراءة والكتابة
والتخزين. - حدود الاستعلامات والعلاقات. - ضرورة تصميم قواعد العزل بدقة.

### الخيار B: PostgreSQL

مناسب إذا احتجت تقارير مترابطة، وعلاقات كثيرة، واستعلامات مالية أو
تحليلية معقدة. يمكن تشغيله عبر خدمة مُدارة، لكنه يضيف مسؤوليات إعداد
وإدارة.

**التوصية:** إذا كانت حاسبتك مبنية على React/JavaScript ولا تحتاج علاقات
معقدة، ابدأ بـFirebase. لا تضف PostgreSQL لمجرد أن SaaS يستخدمها أحياناً.

## 9.3 الاستضافة والدومين

اختر الاستضافة بعد معرفة إطار التطبيق:

-   Cloud Run: خيار مرن لتطبيقات الحاويات وخوادم Node.js وواجهات API.
-   Firebase App Hosting: خيار مناسب لبعض تطبيقات الويب الحديثة، خصوصاً
    الأطر المدعومة مثل Next.js.
-   لا تعتبر GitHub استضافة للتطبيق؛ هو مستودع الكود ومصدر النشر.

اشترِ الدومين عندما يصبح اسم المنتج مستقراً. ثم: 1. أضف الدومين في خدمة
الاستضافة. 2. أضف سجلات DNS المطلوبة كما تعرضها الخدمة. 3. فعّل HTTPS. 4.
اختبر روابط إعادة التوجيه وتسجيل الدخول وروابط البريد. 5. حدّث عناوين
Webhooks المسموح بها وروابط العودة من بوابة الدفع.

# 10. النشر والبيئات

استخدم ثلاث بيئات منفصلة قدر الإمكان:

  البيئة        الاستخدام
  ------------- --------------------------------------------
  Development   التطوير اليومي وتجاربك

  Production    العملاء الحقيقيون والمدفوعات الحقيقية

## قواعد النشر

-   لا تنسخ بيانات العملاء الحقيقية إلى بيئة الاختبار.
-   لا تنشر مباشرة إلى الإنتاج بعد تعديل مولّد بالذكاء الاصطناعي.
-   اجعل كل ميزة في فرع Git مستقل.
-   استخدم Pull Request أو مراجعة فرق التغييرات قبل الدمج.
-   احتفظ بإمكانية الرجوع إلى آخر إصدار مستقر.
-   خزّن الأسرار في Secret Manager أو إعدادات آمنة، لا في المستودع.

# 11. خطة التنفيذ على مراحل مع مخرجات واضحة

لا تبدأ بكل شيء في وقت واحد. هذه هي خطة العمل المقترحة.

## المرحلة 0 --- توثيق التطبيق الحالي

**المهام** - تحديد إطار العمل واللغة وإصدار المكتبات. - تحديد مكان حفظ
البيانات حالياً. - رسم وحدات الحاسبة الحالية. - توثيق الأنواع الأربعة
وقواعدها ومدخلاتها. - إعداد حالات اختبار مرجعية. - حفظ نسخة احتياطية.

**المخرج:** وثيقة فنية للتطبيق الحالي + نسخة Git مستقرة + اختبارات
حسابية.

**شرط الانتقال:** تستطيع إعادة تشغيل التطبيق والحصول على النتائج
المرجعية نفسها.

## المرحلة 1 --- تجهيز البنية والحسابات

**المهام** - إنشاء مستودع GitHub خاص. - إنشاء مشروع Firebase. - إعداد
Authentication. - تحديد هل التسجيل بالبريد وكلمة المرور فقط أم إضافة
Google Sign-In. - بناء صفحة تسجيل الدخول والتسجيل واستعادة كلمة
المرور. - إنشاء Tenant عند التسجيل. - ربط المستخدم بالورشة كمالك.

**المخرج:** يمكن لمستخدم جديد إنشاء حساب وورشة والدخول والخروج واستعادة
حسابه.

**شرط الانتقال:** إنشاء حسابين مختلفين ينتج مساحتين مستقلتين.

## المرحلة 2 --- عزل البيانات

**المهام** - اعتماد نموذج `tenantId`. - بناء قواعد Firestore Security
Rules. - تحديد الأدوار. - نقل/حفظ المشاريع تحت مساحة الورشة. - منع
الوصول إلى بيانات Tenant آخر. - اختبار الوصول المباشر غير المصرح به.

**المخرج:** قاعدة بيانات متعددة العملاء مع عزل مثبت بالاختبار.

**شرط الانتقال:** يفشل أي اختبار يحاول فيه العميل A قراءة أو تعديل
بيانات العميل B.

## المرحلة 3 --- المشاريع والأنواع والأسعار

**المهام** - حفظ مشروع جديد. - عرض قائمة المشاريع والبحث فيها. - فتح
مشروع وتعديله ونسخه وأرشفته. - حفظ تفاصيل الشبابيك ضمن المشروع. - إضافة
الأنواع الأساسية. - إنشاء أنواع قابلة للتهيئة. - إضافة طلب نوع يحتاج إلى
برمجة. - حفظ لقطة المدخلات والأسعار والنتائج.

**المخرج:** يستطيع العميل إدارة دورة عمله دون فقدان نتائج الحساب
القديمة.

**شرط الانتقال:** نجاح اختبارات حفظ واسترجاع وتعديل المشاريع والأنواع.

## المرحلة 4 --- الباقات والتجربة المجانية

**المهام** - تحديد الباقات وحدود كل ميزة. - إنشاء جدول/سجل خطط
الاشتراك. - بناء خدمة تحقق من الصلاحيات. - إعداد تجربة 7 أيام. - حفظ وقت
بداية التجربة ونهايتها على الخادم. - منع التلاعب بتاريخ الجهاز. - بناء
شاشة حالة الاشتراك. - تحديد سياسة ما يحدث بعد انتهاء التجربة.

**المخرج:** نظام تجريبي يمكن اختباره دون تحصيل أموال حقيقية.

**شرط الانتقال:** لا يستطيع العميل تمديد التجربة بتعديل بيانات المتصفح،
ولا يحصل على ميزة غير مشمولة بباقة حسابه.

## المرحلة 5 --- الدفع وحفظ وسيلة الدفع

**المهام** - اختيار مزود يدعم التاجر في الأردن. - تأكيد دعم recurring +
save payment method + trial. - فتح حساب تاجر والتحقق من المتطلبات. -
إعداد Sandbox. - ربط صفحة الدفع المستضافة. - إنشاء الاشتراك التجريبي بعد
نجاح إعداد وسيلة الدفع. - استقبال Webhooks والتحقق من توقيعها. - تفعيل
الاشتراك بعد تأكيد المزود. - تنفيذ إلغاء التجديد. - اختبار النجاح والفشل
والتكرار والاسترداد. - إعداد رسائل البريد الخاصة بالدفع والتجربة.

**المخرج:** العميل يسجل وسيلة دفع قبل التجربة، ولا يُحصّل الاشتراك إلا بعد
7 أيام وفق موافقته.

**شرط الانتقال:** نجاح دورة كاملة في Sandbox، بما فيها الإلغاء قبل
التجربة وفشل الدفع بعد انتهائها.

## المرحلة 6 --- لوحة الإدارة

**المهام** - حسابات الإدارة والأدوار. - إحصائيات المستخدمين
والاشتراكات. - إدارة الباقات. - مراجعة طلبات الأنواع الخاصة. - تمديد
التجربة مع تسجيل السبب. - متابعة حالات الدفع والفشل. - سجل تدقيق.

**المخرج:** تستطيع إدارة المنصة دون الدخول إلى قاعدة البيانات يدوياً.

## المرحلة 7 --- الاختبارات والإطلاق

**المهام** - اختبارات الحسابات والمعادلات. - اختبارات عزل العملاء. -
اختبارات الصلاحيات والاشتراك. - اختبار الهاتف والكمبيوتر. - اختبار
البريد والروابط. - اختبار الدفع التجريبي. - سياسة الخصوصية والشروط. -
النسخ الاحتياطي والاسترجاع. - ربط الدومين وHTTPS. - إطلاق محدود لمجموعة
ورش تجريبية.

**المخرج:** نسخة إنتاجية قابلة لاستقبال أول العملاء.

# 13. التكلفة والتشغيل

لا يمكن تحديد تكلفة شهرية دقيقة قبل معرفة عدد العملاء، وعدد المشاريع،
وحجم الصور/المرفقات، وعدد عمليات الحساب، وحركة الموقع.

ضع ميزانية لكل عنصر:

  البند                     طبيعة التكلفة
  ------------------------- --------------------------------------------
  الدومين                   تجديد سنوي
  Firebase Auth             بحسب الخطة والاستخدام ونوع تسجيل الدخول
  Firestore                 قراءات وكتابات وتخزين ونقل بيانات
  Cloud Run / App Hosting   موارد التشغيل والبناء والنقل
  البريد                    حسب حجم الرسائل ومزود الخدمة
  بوابة الدفع               نسبة/رسوم على المعاملة وقد توجد رسوم دورية
  مراقبة الأخطاء            حسب الأداة والخطة
  النسخ الاحتياطي           حسب حجم البيانات وسياسة الاحتفاظ

**إجراءات ضبط التكلفة:** - ضع تنبيهات ميزانية في Google Cloud. - ضع حدود
استخدام حيث تتوفر. - راقب قراءات Firestore؛ لا تجعل الواجهة تعيد تحميل
كل المشاريع بلا حاجة. - لا تخزّن صوراً أو ملفات كبيرة داخل مستندات
Firestore. - ضع حدوداً منطقية للتجربة المجانية. - راقب تكلفة كل عميل
نشط. - راجع الفواتير أسبوعياً خلال أول شهر.

اشتراك Google AI Pro يساعدك في أدوات الذكاء الاصطناعي، لكنه لا يعني أن
استضافة الإنتاج أو Firebase أو Cloud Run مجانية أو مشمولة بلا حدود.

# 17. التوصية النهائية: كيف تبدأ فعلياً؟

لا تبدأ بالدفع ولا بتغيير الحاسبة. ابدأ بهذه الخطوات الثلاث فقط:

**أولاً:** وثّق التطبيق الحالي، وافهم بنيته، واحفظ نسخة سليمة على GitHub.

**ثانياً:** أنشئ Firebase وأضف التسجيل ونموذج الورشة وعزل البيانات، دون
تغيير منطق الحساب.

**ثالثاً:** انقل حفظ المشاريع والأنواع إلى مساحة كل ورشة، واختبر حسابين
مستقلين.

بعد نجاح هذه المراحل، أضف نظام التجربة والدفع. السبب أن الدفع هو أكثر
جزء يعتمد على مزود خارجي وشروط بلد التاجر، بينما تستطيع بناء واختبار
بقية المنصة قبل دفع أي رسوم اشتراك حقيقية.

**القرار التقني الأهم:** حافظ على محرك حسابات الشبابيك كجزء مستقل، واجعل
الحسابات والمشاريع والأنواع والاشتراكات طبقات منفصلة حوله. بهذه البنية
تستطيع تطوير المنصة وتغيير بوابة الدفع أو الاستضافة مستقبلاً دون إعادة
بناء الحاسبة.

**النتيجة المستهدفة:** منصة SaaS لها دومين خاص، وتسجيل مستقل لكل ورشة،
وتجربة 7 أيام بعد تسجيل وسيلة دفع، وتجديد تلقائي بموافقة واضحة، ومشاريع
وأنواع وأسعار معزولة لكل عميل، ولوحة إدارة كاملة لصاحب المنصة.
